# Localizing strings (heart_language)

User-facing copy lives in `shared/heart_language/lib/l10n/`. `intl_en.arb` is the **source
template** — it defines every key and its `@key` metadata. All other locale files
(`intl_en_CA.arb`, `intl_ru.arb`, …) and the generated Dart (`heart_language*.dart`) are
**derived** from a master CSV and **not committed** (gitignored, like the mocks): `import`
writes them, and a fresh checkout gets them from `make codegen-heart_language`. Three files are
sources and in git: `lib/l10n/intl_en.arb`, `native/l10n/intl_en.arb` (the iOS permission
sentences) and `scripts/translations.csv`.

Round-trip: edit English → **append** the row to the CSV by hand → **import** (regenerates the
locale ARBs and runs `gen-l10n`). Do not run `export` to add or change a string (see below).

Two branches that both add strings no longer conflict: the three sources merge **by key**
through `scripts/l10n_merge.py` (a git merge driver, registered by `make hooks`). The one real
conflict it reports is the same key changed differently on both sides. After any merge, run
`make codegen-heart_language` — the derived files are not in the merge.

## The two commands

Both run from `shared/heart_language/` — the cwd matters, paths inside the script are relative.
(These are the GoLand run configs "export lanuage" and "import translations".)

- **Export** — English ARB → CSV: `dart run scripts/move.dart export`. **Avoid it.** It
  rewrites the whole CSV: rows go into ARB order, every line ends in CRLF, and any row with no
  key in `intl_en.arb` is deleted. The `iosHealth*UsageDescription` rows exist only in the CSV,
  because they feed the native InfoPlist strings. A one-key change comes out as a ~40-line diff.
- **Import** — CSV → locale ARBs: `dart run scripts/move.dart import` (from the repo root,
  `make codegen-heart_language` is the same thing). Regenerates `intl_<locale>.arb` for every
  non-English column in the CSV (copying each key's metadata from `intl_en.arb`), writes the
  native iOS/Android permission strings, then runs `flutter gen-l10n` and `dart format
  --line-length 120` on the generated Dart. After this the `L` getters exist.

## Steps to add or change a string

1. **Edit `lib/l10n/intl_en.arb` only.** Add the key and its `@key` block:
   ```json
   "retry": "Retry",
   "@retry": { "description": "Button to retry a failed action", "type": "text", "placeholders": {} }
   ```
   For a parameterized string, declare its `placeholders` here — metadata is copied to every
   locale on import.
2. **Append the row** to `scripts/translations.csv` with a raw append (`printf '%s\n' '…' >>`
   or an Edit at the end of the file). Never round-trip the file through a CSV encoder or a
   line-based rewrite, because it has quoted multi-line fields. The columns are the header row
   (`head -1`, today `id,description,en,en_CA,ru,es,fr`), and every locale is filled. Quote by
   hand only the fields that contain a comma. The file is LF only.
   To **change** an existing string, make a targeted Edit on that one row.
3. **Translate**: for `en_CA`, usually copy `en`. For `ru`, follow
   `.prompts/translate-en-ru.md` (repo root) — it has the rules: keep tone/emoji, preserve
   placeholders like `{exerciseName}` and ICU plurals verbatim, match label length. If the user
   has their own translation process, hand off here and stop.
4. **Import**: `cd shared/heart_language && dart run scripts/move.dart import`. Regenerates the
   locale ARBs, runs `gen-l10n`, formats.
5. **Use it**: `L.of(context).retry`.

## Facts and gotchas

- **Never hand-edit `intl_en_CA.arb` / `intl_ru.arb`** — they are regenerated by `import` and
  are not in git. Only the two `intl_en.arb` files and `translations.csv` are hand-edited and
  committed; a diff that touches a generated file is a diff that should not exist.
- New locale = add a column to the CSV by hand, then `import`.
- `import` **skips** a locale whose cells are all empty.
- Changed the English wording of an existing key? Edit its row's `en` cell and re-translate the
  other cells, then import. Otherwise the other locales silently keep stale copy.
- The English ARB is the template, not an import target. A row added to the CSV alone generates
  nothing: `git status` showing only the CSV as modified is the tell.
- `import` ends by running `flutter gen-l10n`; you do not need to run it separately.

## Self-check
- [ ] Only `intl_en.arb` was hand-edited (no direct edits to generated locale ARBs)
- [ ] `translations.csv` has the new/changed key with translations filled
- [ ] `git diff --stat -- shared/heart_language/scripts/translations.csv` reads N insertions,
      0 deletions for N new keys, and `grep -c $'\r' shared/heart_language/scripts/translations.csv` is `0`
- [ ] ran `import` (which ran `gen-l10n`) — `L.of(context).<key>` resolves
- [ ] `flutter analyze` clean where the string is used
