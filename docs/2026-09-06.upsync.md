# Link account and upsync the local store

heart-of-yours#96, the app side of heart-api#66. An anonymous session (#91) signs in; everything
the device holds goes to the account. This page is the shape of that: the two cases, the replay
order, what gates the rest of the app while it runs, and how an interrupted run resumes.

## The two cases

Both start from the login page an anonymous session reaches through its profile's no-account
dialog. `Auth` decides which it is (`_linkOrSignIn`, `_fromAnonymous`):

1. **Link** — the Google/Apple credential (or, on sign-up, the email credential) is new to
   Firebase: `linkWithCredential` on the anonymous user. The uid is unchanged; nothing is rekeyed.
2. **Existing account** — linking fails with `credential-already-in-use`, or the user *logged in*
   with email (an account that exists, by definition): the session signs in with the credential
   and the uid changes. `LocalDatabase.rekeyUser` moves every row from the anonymous uid to the
   account's in one transaction — workouts, templates, folders, customs, unit preferences, charts,
   goals, the device's health samples and their backfill markers — with the anonymous row winning
   a natural-key collision against an earlier mirror of the account on the same phone.
   `Preferences.rekeyUser` moves the theme preset and the two health answers the same way.

Either way `Auth` calls `onLink(fromUid, toUid)` **before** the new user is adopted, so the app
(`app.dart`) can `Upsync.claim` — rekey where needed and record that a replay is owed — before
any notifier is keyed on the new uid.

## The gate

`RemoteAccess` now has two flags: `account` (Auth's: there is an account) and `replaying`
(Upsync's: the store is still being replayed into it). `allowed` is `account && !replaying`.

From the moment a sign-in starts from an anonymous session until the replay completes, the
incidental remote legs stay closed: `syncPendingWorkouts`, `Goals.pushPending`, the history and
template pulls. Otherwise they would post the same rows out of order — a workout referencing a
custom exercise the server has not seen yet — and pull the account's view over a mirror that
had not reached it. The replay talks to the server directly through `Api`, and opens the leg
when it is done; `_resync` in `app.dart` then runs the pulls once.

A launch under an account whose replay is unfinished (`Upsync.restore`) holds the leg the same
way and resumes the run once the API has its token.

## The replay

`Upsync.run` (heart_state) — not a sync engine. Six passes over the store, in the order the
server contract fixes (later resources reference earlier ones):

1. custom exercises → 2. unit preferences → 3. template folders → 4. templates → 5. workouts →
6. goals.

Every create sends the app's own v7 uuid; the server answers `201` (created) or `200` (already
there, by id — or by *name* for customs and folders). A `200` under a **different** id is a
name-merge: `LocalDatabase.mergeExercise` / `mergeFolder` rewrite every local reference (workout
and template exercises, unit preference, goals, chart preferences; templates' `folder_id`) before
anything downstream is sent, and drop the merged row.

Each confirmed row is written back through the same local service the notifiers use
(`storeWorkoutHistory` marks the workout synced, `reconcileGoalId` the goal, …) and recorded in
the **ledger** (`upsync` table, v13) with its outcome. Pending = rows under the uid minus the
ledger, so a resumed run — after a killed app or a dropped connection — posts nothing twice, and
the "n uploaded, n already there" line counts across every attempt. When nothing is pending the
debt (`syncs` row `upsync:<uid>`) and the ledger are dropped together.

Refusals are final and skipped: `403 id_taken` (should never happen; reported to Sentry) and a
goal over the cap (`400 goal_limit`) are recorded as skipped and left alone locally; the run goes
on. Anything else — the server unreachable — stops the run where it is, retryable from the row.

Rows written while the run is under way (a workout finished with the leg closed) are caught by a
further pass; the loop stops when a pass finds nothing.

Templates minted before this ticket carry a timestamp for an id. The server validates the shape,
so `Api.saveTemplate` leaves such an id off and reconciles with the one the server mints —
`startTemplate` mints v7 uuids from now on.

## The UI

`UpsyncRow`, a sliver at the top of the profile: a line with a bar while running
(`upsyncRunning`), the line with a Retry button when the server could not be reached
(`upsyncFailed`), one line of numbers with a dismiss when done (`upsyncDone`, plus `upsyncSkipped`
when some rows were refused). Absent otherwise. No dialog, no interstitial, nothing elsewhere.

## Health data

Nothing here reads a health table: `UpsyncService` has no health method, and the replay's plan
is built from the exercise, template, workout and goal services only. The rekey moves health
samples between uids *on the device* — the same store, the same phone. See
`docs/2026-09-05.health-data.md`.
