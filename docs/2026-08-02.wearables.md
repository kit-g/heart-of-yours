# Health data and wearables — survey and settled decisions

The ask: start integrating with wearables soon; collect the user's health data with permission,
possibly weather, and build a health narrative on top — in an app whose whole posture is *collect
generously, present it back for free, don't paywall the user's own data*.

## Decisions (settled)

1. **Phone app only. No watch app, in any form, for now.** Flutter does not run on watchOS, so an
   Apple Watch app is a hand-written SwiftUI target sharing no code with Heart — weeks of work
   duplicating every string and every set row. The overwhelming majority of the value does not
   require one (see §1). Revisit once the data is flowing and there is evidence people want the
   wrist.

2. **Apple / HealthKit first.** The lightest lift: the entitlement is a checkbox on an account we
   already have, and there is no store-review gate on the way in. Android's Health Connect is the
   same shape and the same package, but carries a Play declaration review — so it lands second, not
   never.

3. **Health data is device-only, and that is a feature, not an implementation detail.** Nothing
   health-related goes to heart-go. Not raw samples, not derived aggregates, not weekly rollups. This
   is stated in the UI, in plain copy, as a thing Heart does deliberately. See §6 — including the
   two leak paths that would quietly make it a lie.

4. **The narrative is computed on-device**, as a consequence of 3. This is consistent with the rule
   already settled in the goals doc — *the server stores definitions, the app computes progress
   locally, because that's the only thing that's correct offline*. Health data follows suit. No
   `synced` column on any health table.

5. **Go wide incrementally, and never per-vendor.** Non-Apple wearables are reached through the OS
   store, not through vendor integrations (§5). There is no Garmin project, no Whoop project.

### What decision 3 buys

It deletes, outright: the Google Play health-data declaration review, most of the Apple 5.1.3
conversation, the breach blast radius, the `synced` column, the reconciliation logic, and the
question of what happens when two devices disagree. That is a very large amount of work and risk
removed by a decision that also happens to be the better product.

### What it costs

No push notifications driven by health data ("your sleep's been short all week — consider a deload").
No cross-device continuity of health-derived state. Both are real; neither is worth the trade.

## 0. What is built

Tier 0, plumbing and first UI.

- **`shared/heart_health`** — `HealthService` over the `health` plugin, with `HealthMetric` /
  `HealthSample` as our own vocabulary so the plugin's types never reach state or UI. Split into
  `models.dart` (no plugin) and `heart_health.dart` (plugin) so `heart_db` can persist a sample
  without pulling a platform channel. Web and desktop get `UnsupportedHealthStore` via a conditional
  export. 48 tests.

  One of them exists because running the app said so: on iOS a read before anyone has been asked
  throws `HEALTH_ERROR — Authorization not determined`, and we were logging that at `WARNING` once
  per tracked metric on every cold start. It is the normal case, not a fault — HealthKit will not
  answer `access()` honestly, so attempting the read *is* how we find out. Now logged at `fine`,
  with the match kept deliberately narrow so a genuine query failure stays a warning.
- **`heart_db` migration 0009** — `health_samples`, keyed on the platform's own sample UUID so an
  overlapping re-read collides instead of duplicating. No `synced` column, deliberately. Daily
  rollups reconcile across sources rather than summing (see below). 16 tests against real in-memory
  SQLite, because the reconciliation *is* the logic.
- **`Health` notifier** in `heart_state`, registered in `app.dart`, per-metric incremental sync off a
  stored watermark, and an **unbounded backfill** — everything the store has, floored at
  September 2014 because HealthKit shipped with iOS 8 and Health Connect is younger. A year-long
  mirror would have made the chart's zoom-out a lie.

  Three things that backfill cannot be naive about. It is **chunked** at 90 days, because the store
  answers with every sample in the window at once and a decade of step counts is hundreds of
  thousands of objects in memory. It is **recent-first across all six metrics before any of them
  walk backwards**, so the dashboard fills in seconds while the past arrives behind it. And it is
  **resumable**: progress is written to the `syncs` table after every chunk, keyed per user and
  metric, so an app closed mid-walk picks up where it stopped. That marker is also why the walk
  terminates — "we found nothing in 2015" and "we never looked at 2015" are the same answer from a
  query, so without it a user with no old data would re-read six empty years on every launch.

  28 tests, which found two bugs worth recording because
  neither is visible from `heart_health` or `heart_db` in isolation:
  - `sync` guarded on a plain `_syncing` flag, so tapping connect while the launch backfill was
    still running dropped the sync that was supposed to read what the user had just granted. It now
    coalesces onto an in-flight future, and `connect` awaits that pass before starting a fresh one.
  - `status()` was read once at launch. If it threw, `_status` stayed at its `unavailable` default
    and the sync gate never reopened for the rest of the session — on iOS there was no recovery path
    at all. `connect` re-reads it.
- **The dashboard section** — `presentation/widgets/health/section.dart`. Four states, driven off
  `hasData` rather than any permission check: absent where there is no store, an invitation, the
  honest empty state, and the cards. Deliberately *not* a `ChartPreferenceType` — see the answer to
  open question 1 below. 13 widget tests.

  It sits between the profile area and the exercise chart grid, not below the grid as first drafted.
  Health is page-decided, like the aggregation chart and the goals card beside it; below the grid the
  invitation would have sat under however many exercise charts the user keeps, which for a first-run
  prompt means never being found. Every state wears the same header as the goals card next door, so
  "On this device" is on screen from the first moment rather than only once there is data.
- **The metric detail** — `presentation/widgets/health/detail.dart`, opened by tapping a card. The
  sparkline beside a card is a *shape*: no axes, no scale, bucketed to 24 points so a quarter of
  spiky daily data still reads as a trend. Right on 96pt, useless for "how much, when". The detail
  is the app's own `HistoryChart` — the same axes, grid and tap-to-pin as every other chart in
  Heart — over every day held. Formatting moved to `health/metric.dart` so a reading cannot say
  81.5 kg on the card and 179.7 in the chart.

  **Density is the whole problem, and more data is the wrong answer to it.** A year of daily
  readings is 365 points across ~240pt of plot — two thirds of a point each. Drawn faithfully, a
  spiky metric stops being a line and becomes a filled block with a ragged top: more data, less
  information.

  That is what `presentation/widgets/timeline_chart.dart` exists for, and it is **not health-only**
  — the per-exercise charts use it too. One piece of state, the number of days on screen: chips
  jump to a named window, a horizontal drag scales it continuously, and **granularity is never
  chosen, only derived** — day up to 100 days, then week, month and year, so the plot holds roughly
  25–65 points at every scale. The caption names the scale whenever a point is a mean, because a
  chart quietly showing a smoothed point where the header shows a day's reading lies by omission.
  Chips are filtered to windows the series can actually fill: offering a year to someone with three
  weeks of history is a control that does nothing.

  `HistoryChart` gained four knobs for it, all defaulted to previous behaviour so no other chart
  moved: `showDots`, `barWidth`, `leftAxisSize` and the existing `topLabel`. `leftAxisSize` is why
  the chart looked shoved right — the shared 60pt reserve is sized for `1:30:00`, and health labels
  are `300` / `12K` / `8h 0m`, so `HealthMetric.axisWidth` reserves 34–46 and gives the rest back.

  The per-exercise charts were capped at **30 sessions** — a few weeks for anyone training
  seriously, which made them a snapshot rather than a history. Now 5000, since the chart can travel.
  Dashboard chart cards keep the old fixed rendering (`ExerciseChart.timeline` defaults to false):
  the controls need room a tile does not have.

  Two things a real store taught this axis. **Month names need their year** once the window crosses
  one: a three-year view labelled `Aug — Feb — Aug — Feb — Aug` is three different Augusts wearing
  the same label, so the month grain switches to `DateFormat.yMMM` when the visible points span
  more than one year (and drops to four labels, since each is half as wide again). And **the app
  supported only `Locale('en')`**, so a Canadian phone fell back to US conventions and read June
  the 19th as `6/19`. `en_CA` is not a translation — it is the same copy under different date
  conventions (`06-19`) — so it is now supported while the actual translations wait. Every date in
  the app goes through `DateFormat(…, localeName)`, which makes the resolved locale the whole of
  that behaviour.

  One trap: the content needs an explicit width. `AlertDialog` wraps its column in an
  `IntrinsicWidth`, `HistoryChart` contains a `LayoutBuilder`, and that pairing throws
  *"LayoutBuilder does not support returning intrinsic dimensions"* and renders **nothing**. A
  `SizedBox` answers the intrinsic query without descending into the chart.

  A card with a single reading is deliberately inert: one dot is not a trend, and the sparkline is
  already blank for the same reason.

  **The sparkline draws the same window its detail opens on** — `TimelineRange.quarter`, from one
  constant. It used to draw the whole series, which was a year while `_backfill` capped the mirror
  and silently became *however far back HealthKit goes* the moment that cap was lifted. A thumbnail
  showing three years beside a detail showing three months cannot agree about the shape of
  anything, and nothing in either surface said which was which.
- **The settings block** — `presentation/widgets/health/settings.dart`. Names exactly what is read,
  restates where it stays, routes into the OS permission, and deletes the local mirror. 10 tests.

  It is also the feature's only permanent home: the dashboard invitation is gone for good once
  dismissed, so without this there is no way back in. Three details worth keeping: the first tap
  *asks* rather than opening system settings, because Heart does not appear under the OS health
  permissions until it has asked once; every later tap goes to the Health app rather than to this
  app's page in the OS settings (finding 4 below); and the delete is offered only when there is
  something to delete, since a button that clears nothing still claims to have worked.
- **`reportHealthFailure`** in `lib/core/env/sentry.dart` — reports the exception *type* and stack
  trace and drops the message. Not theoretical: a sqflite error carries the failing SQL **and its
  bound arguments**, so an insert that blew up would have shipped a heart rate to Sentry inside the
  error string.
- **iOS** — HealthKit entitlement in both `.entitlements`, and `NSHealthShareUsageDescription`, which
  is where the device-only promise first meets the user.

Four findings from building it that changed the design. The last one only appeared on a real
phone:

1. **iOS will not disclose read permission.** `requestAuthorization` returns whether the *sheet was
   shown*, not whether anything was granted — HealthKit refuses to say, because "you may not read
   heart data" leaks that the user has heart data to hide. Modelled as `HealthAccess.unknown`.
   Consequence for the UI: **there is no "Connected ✓" state to render.** `Health.hasData` is what to
   branch on, and it correctly collapses "declined" and "granted but empty" into one honest state.
2. **The dedup problem is worse than a dedup problem.** The plugin's `removeDuplicates` is a
   `LinkedHashSet` — it catches identical samples, and does nothing about the phone, the watch and a
   synced third-party app each reporting the same hour's steps as *distinct* samples. A plain `SUM`
   multiplies the user's step count by however many devices they own. Cumulative metrics now total
   per source and take the best-covered one; instantaneous metrics average.
3. **HRV is two different metrics.** Apple exposes SDNN, Health Connect exposes RMSSD. Both are
   milliseconds, both collapse into one `HealthMetric`, and they routinely differ by a factor of two.
   Flagged `isPlatformDependent` — a chart must not plot one against the other, and a narrative must
   not describe a user switching phones as a change in their body.
4. **HealthKit permissions are not in the app's iOS settings page, and the app cannot link to
   them.** Both "review what Heart can read" affordances called `AppSettings.openAppSettings()`,
   which on iOS opens Settings › Heart — cellular data, Siri and search, and no mention of health
   whatsoever. A user who declines the sheet and then follows the app's own advice lands somewhere
   with nothing to change and no signal they are in the wrong place. Read access lives in the
   **Health app**, under the user's profile, and Apple publishes no deep link to an app's row there:
   the best available handle is the undocumented `x-apple-health://`, which opens the summary screen
   and leaves two unsignposted taps to the user.

   Now `HealthService.openPermissions()`, so the "where do permissions live" question stays behind
   the same interface as the plugin's vocabulary. It returns false where the platform has nowhere to
   send anyone — Android's Health Connect settings need an intent that neither the plugin nor
   `url_launcher` can fire — and only then does the caller fall back to the app's settings page,
   which on Android is at least the right building. The button's label follows the destination
   (`healthOpenHealthApp` on iOS, `healthOpenSettings` elsewhere): a control that says "open
   settings" and opens the Health app is the same failure pointed the other way.

   **Not reproducible on a simulator**, which is why it survived to a device: the simulator has no
   Health app, so `openPermissions` fails there and takes the Android fallback path.

   The trip out has a second half. Permissions change in *another app*, so the only moment Heart
   can act on is coming back — and it was doing nothing with it, leaving the user staring at the
   card that had just sent them away. `Health.onResume`, driven by the app's one
   `AppLifecycleListener` in `_AppState`, re-reads on return; the throttle it applies to ordinary
   resumes (15 minutes, so alt-tabbing costs nothing) is deliberately bypassed after a permission
   trip, which is the one case where the answer really may have changed.

   And because a first backfill is a year across six metrics, "came back and nothing happened" has
   a slower cousin: an empty state asserting there is no data *while the read that would disprove
   it is still running*. Whenever `Health.syncing`, the dormant header shows a spinner instead of
   its tooltip icon.

   **The asked-and-empty state is now the header and nothing else** — greyed, with one icon button.
   The card it replaces stated a fact the user could not act on from that page and did so on every
   launch, which is the definition of nagging; the two situations behind it are indistinguishable
   to us anyway. `healthEmptyBody` is gone with the card.

   The button opens a **dialog**, not a tooltip. A tooltip was the first attempt and it failed on
   device for a reason worth keeping: explaining is the smaller half of the job. Knowing that the
   permission lives in another app does not get anybody there, and a tooltip cannot carry a
   control. The dialog says where the permission is and then goes there.

   **The copy is an instruction, not an explanation.** The dialog body and the settings-page
   subtitle both say the same thing — "tap your profile picture, then Apps" — because that is what
   is left to do once the button has opened Health, and Apple publishes no deep link to an app's
   row. An intermediate version replaced the path with *why* the permission lives outside Heart;
   that is a finding from building this, and findings do not belong in the UI. If the path ever
   goes stale, replace it with the new path rather than with prose.

   The heart icons take `colorScheme.primary` when [Health.hasData] — the nearest thing to a
   "connected" light this feature is permitted to have, given the section above.

   **Revoking access does not delete the mirror**, and cannot sensibly: iOS never reports a
   revocation — reads just stop returning anything — so "they turned it off" is indistinguishable
   from "they haven't worn the watch", and deleting on that signal would throw away a year of
   history over a weekend off the wrist. Erasing stays where the user put the intent: the explicit
   delete in settings, and sign-out.

Also dropped: **VO₂max**, which the doc promised. The `health` package does not expose it on either
platform. Not worth a fork; revisit if it lands upstream.

Two things used to be worth watching here, both about the `health` package rather than our code.
**`health` 13.3.2, published 2026-08-14, closed both of them in one release:**

- **Swift Package Manager is supported.** 13.3.1 shipped only a `health.podspec`; 13.3.2 ships
  `ios/health/Package.swift`. Until then the build warned *"The following plugins do not support
  Swift Package Manager for ios: health"* and fell back to CocoaPods, which meant the Podfile had to
  stay for one plugin while the rest of the project moved to SPM — and Flutter had said that
  fallback "will become an error in a future version". This was the single thing most likely to
  force a different Tier 0 dependency.

  CocoaPods is now gone from the project entirely: `pod deintegrate`, the `Podfile` and
  `Podfile.lock` deleted, the `Pods-Runner` includes stripped from both `Flutter/*.xcconfig`, and
  the dangling `Pods/Pods.xcodeproj` reference removed from `Runner.xcworkspace`. The build says
  *"All plugins found for ios are Swift Packages"* and dropped from **85.1s to 44.7s**.
- **The `device_info_plus` override is gone.** `health` capped it at `^12` (win32 5) while
  `package_info_plus` needed win32 6, so the two could not co-resolve without a
  `dependency_overrides`. 13.3.2 asks for `^13.2.0` and the app resolves cleanly with the override
  deleted.

### The alternative: `health_connector`

**Decided: stay on `health`, and 13.3.2 settles it further.** The strongest argument for moving was
that `health_connector` supported SPM and `health` did not; that argument no longer exists. What
follows is kept because the wrapper makes the option cheap to revisit, not because there is a plan
to move. The remaining draws are VO₂max and first-class workout write-back for Tier 1 — neither
urgent, and both weighed against a dependency eight months old with one maintainer.

Worth a spike, and cheap to try — the wrapper did its job. **Exactly one file imports the plugin**
(`heart_health/lib/src/device.dart`, 226 lines). The other 664 lines of the package, all of
`heart_state` and all of the UI speak `HealthMetric`/`HealthSample` and would not move.

What it would resolve:

- **SPM natively.** `health_connector_hk_ios` ships `ios/health_connector_hk_ios/Package.swift`.
  That removes the one plugin holding the Podfile hostage.
- **VO₂max**, which this doc records as dropped because `health` does not expose it.
- **Writing workouts back** — first-class `ExerciseSessionRecord` support on both platforms, which
  is all of Tier 1.
- Possibly the `device_info_plus` override, which exists only to work around `health`'s constraint.

It also, independently, documents the same thing we discovered the hard way: iOS *"purposefully
restricts access to read authorization status"* and it returns `unknown` for every iOS read
permission. An author who leads with that understands the domain.

Against it, and it is not nothing: **published 2025-11-23, 33 versions in eight months, 21 likes, 13
GitHub stars, one maintainer**, versus `health`'s 673 likes and a university research centre behind
it. For a feature whose failure mode is *invisible to us by construction* — health data never
reaches heart-go and is deliberately scrubbed out of Sentry — a dependency churning weekly is a
real risk. We would not find out it had started returning wrong numbers.

So: prototype it behind `HealthService`, run both against the same phone, and compare. The
27 tests in `heart_health` already pin the contract, and §8's point stands — multi-source
deduplication is the part that only shows up on a real device with a real watch and years of
samples. That comparison, not the pub.dev scores, is what should decide it.

**`spike_flutter_sdk` is ruled out on decision 3, not on merit.** It exists to send health data to
SpikeAPI's backend — "automatic formatting and sending to the SpikeAPI". Device-only is the whole
promise; a dependency whose purpose is uploading the data cannot be reconciled with it, whatever its
coverage of Garmin and Whoop.

## 1. The mental model

"Wearable integration" is three unrelated bodies of work that get conflated constantly.

**Axis A — the OS health store.** HealthKit (iOS) and Health Connect (Android) are databases on the
phone. Watches write into them; your app reads out of them. **You do not need a watch app to get
watch data.** If the user wears an Apple Watch, their resting heart rate, HRV, sleep, steps, body
mass, active energy and VO₂max are already sitting in HealthKit on the phone Heart is running on.
This is where nearly all of the value is, it is by far the cheapest axis, and per decision 5 it is
also the *only* axis we treat as wearable integration.

**Axis B — a watch app.** A UI on the wrist. Ruled out for now (decision 1). For the record when it
is revisited: watchOS means SwiftUI, no code sharing, 3–5 weeks for a glance-and-control app and
another 4–6 for standalone logging. Wear OS does run Flutter, being Android, at roughly 3–4 weeks —
but only worth it if the Android install base justifies it, which is a number already in Firebase
Analytics.

**Axis C — third-party device clouds.** Garmin, Whoop, Oura, Fitbit. Not app work: OAuth + webhook
integrations that would live in heart-go. Ruled out by decision 3, because they cannot exist without
server-side storage (§5).

The most important consequence:

> **Live heart rate during a lifting set requires a watch app** — continuous sampling only happens
> while an `HKWorkoutSession` runs *on the watch*. From the phone we get retrospective samples:
> whatever the Watch recorded, readable after the fact. "Show my BPM as I press" is Axis B. "Show
> what my heart did during yesterday's session" is Axis A, and is nearly free.
>
> The exception is a BLE chest strap (§5), which delivers live in-set HR to the phone with no watch
> app at all.

## 2. What the app already has

The codebase is in unusually good shape for this. Specifics, because they change the estimates:

**A native bridge precedent exists.** `MethodChannel('me.heart/device')` is already wired
(`lib/core/env/sentry.dart:32`, `android/app/src/main/kotlin/me/heart/MainActivity.kt:13`).

**Local-first with a real migration ladder.** `heart_db` is at schema v5 with an ordered migration
map (`shared/heart_db/lib/src/migrations/index.dart`). Health samples land as migration 0006.

**Lazy permission-asking is already the house style.** `ensureNotificationPermission`
(`lib/core/env/notifications.dart`) deliberately does *not* prompt at launch — it asks the first time
the user sets a rest timer, and `remindNotificationsOff` offers a settings shortcut if refused.
Health permission should be requested exactly this way: at the point the user asks for the feature,
never on a launch screen. It is also the only way a HealthKit prompt reads as honest.

**Charts have a home and a vocabulary.** `heart_charts` is a package; `ChartPreferenceType` is an
11-value enum mapped to SQL in `heart_db/lib/src/metrics.dart`; the profile dashboard renders a
user-reorderable list of chart preferences.

**Everything is stored metric.** Weights in kg, distances in km, converted only at the display edge
(`Preferences.weightValue`). HealthKit's canonical units are also kg and metres — no conversion
layer, and a whole category of bug removed.

**Two deferred features are blocked on exactly this work.** The goals doc rules body-measurement
goals out of scope with: *"No body metrics are collected. Revisit when they are — it lands as another
`GoalMetric` + a source table, not a new feature."* Reading body mass from HealthKit unblocks that,
and the landing spot is already designed.

**`Settings.extra` absorbs new toggles with no backend change.** `Settings` (heart_models) preserves
unknown keys by design — though note that a device-only feature arguably belongs in local
`Preferences` (SharedPreferences) rather than in server-synced `Settings` at all. Consistency with
decision 3 says local.

### What is missing

- No location capture anywhere. Weather would need it.
- `heart_models` lives in the **heart-go repo**, pulled by git ref `main`. Health data has no backend
  component, so **it should not touch `heart_models`**. The service interface goes in the app or a
  new `shared/heart_health` package, keeping the dependency one-directional and the cross-repo
  release cadence out of the picture.

- **Keys for driving.** `AppKeys` / `WorkoutKeys` grew on this branch, which is what makes Flutter

## 4. The work, cheapest first

Rough calendar estimates, single developer, including tests and localized strings.

### Tier 0 — Read HealthKit. ~1 week. This is the project.

`health` (pub.dev, carp.dk, v13.3.1, 673 likes, ~138k downloads) wraps HealthKit and Health Connect
behind one Dart API. Mainstream choice; the alternatives are either much newer with negligible
adoption or vendor SDKs.

Scope: heart rate (resting + samples), HRV, sleep stages, steps, active energy, body mass, VO₂max.

Shape it like everything else here:

- `HealthService` interface + implementation in a new `shared/heart_health` package. **Not** in
  `heart_models` — no backend involvement, so no cross-repo coupling.
- `heart_db` migration 0006: a `health_samples` table — type, value, unit, start, end, **source** —
  plus daily-rollup queries in the `metrics.dart` style. No `synced` column (decision 4).
- `Health extends ChangeNotifier` in `heart_state`, registered in `app.dart`'s `MultiProvider`,
  taking `userId` in the same `onUserChange` block as everything else, implementing
  `SignOutStateSentry`.
- Permission requested at point of use, mirroring `ensureNotificationPermission`.
- Presentation: worth a design pass on whether health metrics join `ChartPreferenceType` and the
  reorderable dashboard, or get their own surface. `ChartPreferenceType` is per-exercise by
  construction; health metrics are not.

**Store the source of every sample.** HealthKit's `HKSource`/`HKDevice`, Health Connect's
`DataOrigin`. Two reasons, one of them urgent:

1. **Deduplication is a real trap.** HealthKit will happily hold steps from the phone *and* the watch
   *and* a third app for the same hour. Naive summation double-counts, badly. Design for it on day
   one rather than discovering it in a shipped chart.
2. It enables honest attribution — "resting HR, from your Garmin" — which is cheap once the column
   exists and impossible to backfill later.

The pleasant surprise: this alone gives "your resting HR trended down over the twelve weeks you were
squatting" — a genuine narrative — with no watch app whatsoever.

### Tier 1 — Write workouts back to HealthKit. ~2–3 days.

On `finishActiveWorkout`, write an `HKWorkout`. Same package, `WRITE` permission.

Small effort, disproportionate perceived value: the user's Activity rings credit their lifting, and
every other app on their phone can see Heart sessions happened. Note this is a *write to the user's
own device store*, entirely consistent with decision 3.

One honesty constraint: **don't fabricate calories.** Without a watch session there is no energy
measurement, only an estimate from bodyweight and duration. Write duration and activity type; leave
energy nil. An invented number that disagrees with the Watch's own is worse than an absent one.

### Tier 2 — Health Connect (Android). Read path landed 2026-08-16; Play review outstanding.

Verified on a Pixel 7 running Android 16. Four things bit, none of them guessable from the Dart
side:

- **`MainActivity` must extend `FlutterFragmentActivity`.** The plugin registers an
  `ActivityResultLauncher` for the permission sheets, and `registerForActivityResult` needs the
  fragment lifecycle. On a plain `FlutterActivity` it logs `Permission launcher not found` and
  every request fails silently — indistinguishable, from Dart, from a user declining.
- **History access is a second, separate grant, and the UI has to say so.** Health Connect keeps
  past-data access away from the permission list a user actually sees, so someone who grants
  everything in front of them is still capped at 30 days and has no way to know it. Both routes into
  permission now say it in as many words — the settings row carries "Past data is a separate switch
  there", and the dormant-section dialog ends "Allow past data too, or charts stop at the last 30
  days". Prompting for it is not enough: a declined or missed prompt leaves no trace on either
  screen.
- **History access is a second, separate grant.** `READ_HEALTH_DATA_HISTORY` in the manifest does
  nothing on its own; without `requestHealthDataHistoryAuthorization` every read stops 30 days back
  however far the backfill walks, and a withheld window and an empty one are the same empty list.
  It is now asked for on both routes into permission — `connect`, and the return leg of a
  permissions trip, because a user who grants in the platform's own settings never passes through
  `connect` at all.
- **The intent for Health Connect's settings has moved, twice.** It began as the androidx action,
  which on Android 16 resolves to nothing; the platform's `MANAGE_HEALTH_PERMISSIONS` would land on
  *this app's* row but is barred to normal apps (`SecurityException: requires
  GRANT_RUNTIME_PERMISSIONS`, signature-level). `HEALTH_HOME_SETTINGS` is the one that works, with
  the androidx action kept as a fallback for Android 13 and earlier. Fired from `MainActivity` over
  `healthPlatformChannel`, since an implicit intent is not a URL and `heart_health` has no native
  side of its own.
- **A stale Settings task will lie to you.** Two rounds of "it still lands on App info" were a
  Settings task left open from an earlier attempt resurfacing its old page. `adb shell am force-stop
  com.android.settings` before each attempt, and read `dumpsys activity activities` rather than the
  screenshot.

Permissions are the six `Health.tracked` reads and nothing else — no writes, no background reads.
The `ViewPermissionUsageActivity` alias is required from Android 14 for the system's "why does this
app have my health data" route.

### Tier 2 — the review, still outstanding.

Same package, same `HealthService` interface, mostly a matter of permission declarations and
manifest entries. The code is small; **the Google Play health-data declaration requires a review
round measured in weeks**, and has delayed releases for people. Start the paperwork early, ship the
code when it clears.

Decision 3 helps here too: a device-only app has a much simpler declaration to make.

### Tier 3 — Weather. ~3–4 days, deferred.

Capture coarse location at workout start, resolve conditions via Open-Meteo (free, no API key, and a
historical archive endpoint — so store coordinates eagerly and resolve lazily, never blocking the
workout-start path on a network call). Needs `NSLocationWhenInUseUsageDescription`.

Deferred and honestly rated: weather is the weakest data source for narrative purposes. *"You lift
heavier in cold weather"* is the kind of finding that is almost always noise at single-user sample
sizes. Cheap and charming; not the thing that makes the feature. It is also the one item here that
would need a backend column to survive a reinstall, which now sits awkwardly against decision 3.

### Tier 4 — The narrative.

The point of all of the above, and it cannot start until Tier 0 has been collecting for weeks — a
narrative over two days of data is a party trick. **Budget the collection lead time explicitly.**
Computed on-device (decision 4), which shapes what is feasible: correlations and trends in SQLite,
rendered locally; not a large model writing prose about your sleep.

## 5. Going wide: non-Apple wearables

**The OS store *is* the non-Apple integration.** There is no per-vendor work. Garmin Connect, Oura,
Whoop and Samsung Health all write into Health Connect on Android and (mostly) HealthKit on iOS, so
the same `health` call that reads an Apple Watch reads all of them. This is what makes decision 5
possible: going wide costs nothing beyond Tier 2.

Rough coverage — worth re-verifying against vendor docs, this shifts:

| Device               | → Health Connect (Android) | → HealthKit (iOS)           |
|----------------------|----------------------------|-----------------------------|
| Samsung Galaxy Watch | ✓ via Samsung Health      | — (Samsung Health left iOS) |
| Pixel Watch / Fitbit | ✓ via Fitbit app          | **✗ — the known holdout**  |
| Garmin               | ✓                         | ✓                          |
| Oura                 | ✓                         | ✓                          |
| Whoop                | ✓                         | ✓                          |
| Withings / Polar     | ✓                         | ✓                          |

Fitbit-on-iOS is the one real gap and it is long-standing. Confirm whether Google has changed it
before promising anything.

**What the OS store will not give you** are the vendors' proprietary composites — Whoop
Strain/Recovery, Oura Readiness, Garmin Body Battery. Those are what they sell, and they stay behind
their APIs deliberately. You get the underlying signals (HR, HRV, sleep stages), not the score. For a
narrative that is arguably better: compute our own view rather than relaying theirs.

**Cloud APIs are ruled out by decision 3, structurally.** Ranked by ease if ever revisited: Withings
(genuinely open, self-serve) → Oura v2 → Polar AccessLink → Fitbit Web API (self-serve, rate-limited,
in flux under Google) → Whoop → Garmin (partner application, approval-gated, not easy). But every one
of them needs a server: OAuth refresh tokens have to live somewhere, webhooks need an endpoint, and
background sync means a backend polling on the user's behalf. There is no device-only version of a
cloud integration that isn't brittle. **The OS store is the only wearable-agnostic path that keeps
data off our servers** — which makes decision 5 a consequence of decision 3, not an independent
choice.

**The one genuinely interesting alternative: BLE chest straps.** Polar H10, Wahoo TICKR, Garmin HRM
speak the standard Bluetooth Heart Rate Service (`0x180D`). Any app can connect with
`flutter_blue_plus` — no vendor API, no account, no cloud, no partner program, nothing stored
anywhere but the device. It is **the only way to get live in-set heart rate without writing a watch
app**, which makes it a real alternative to Axis B rather than a curiosity. Not for everyone, but the
lifters who would want it already own a strap. Worth prototyping after Tier 0.

## 6. Device-only as a product feature

Decision 3 is a promise made in copy, which means it is also an engineering constraint. Both halves
need care.

**Be precise, because overclaiming privacy is the one thing that actually burns you.** *"Your health
data never leaves your device"* is true. *"Heart stores nothing"* is false — workouts sync to
heart-go, and always have. The copy has to draw that line cleanly, or the first person to notice
network traffic reads the whole claim as marketing. The distinction is defensible and easy to state:
your training log is yours across devices; your body's data is yours on this device.

**The OS store is the backup, and that is the story.** Device-only usually implies "lose your phone,
lose your history". Here it doesn't: HealthKit persists across reinstalls and restores to a new
phone, so Heart rehydrates by re-reading it. Nothing is lost by not storing it — which is exactly why
the promise is cheap for us to make and worth making loudly.

**Two leak paths would quietly make the claim a lie:**

1. **Sentry.** `sentry_flutter` is wired app-wide, and `onError: reportToSentry` is passed into
   nearly every state class. A health value in an exception message, a breadcrumb, or a state dump
   ships it to a third party. Health-related errors need scrubbing at the boundary — and a test that
   fails if a health field ever appears in a Sentry payload.
2. **The feedback package.** `feedback: ^3.1.0` captures **screenshots** and uploads them. A user
   reporting a bug from the profile dashboard sends a picture of their resting-HR chart to our
   backend. Either exclude health surfaces from feedback capture, or say so in the copy. This one is
   easy to miss and directly contradicts the headline claim.

   **Closed.** `RedactedInCapture` (`presentation/widgets/redacted.dart`) wraps every health value
   and its sparkline. The package has no per-widget exclusion, so the values take themselves off
   screen while `FeedbackController.isVisible` — redacted rather than blanked, because the user is
   annotating the screen while they look at it and a number that silently vanished reads as a
   rendering bug. It short-circuits when `allowsFeedbackFeature` is off: no reporter, no screenshot,
   nothing to hide from. Two tests, one of which drives an actual capture.

Neither was hard to fix. Both would have been much harder to fix after the promise was on the App
Store page.

## 7. Gates that remain

Substantially shorter than it would have been:

- **HealthKit entitlement** — a checkbox on the developer account we already have (Apple sign-in is
  configured in `ios/Runner/Runner.entitlements`). Not a project.
- **Info.plist strings** — `NSHealthShareUsageDescription` is written and verified on device: it
  renders as the "App Explanation" at the foot of the permission sheet. `NSHealthUpdateUsageDescription`
  was deliberately **absent**, because we no longer ask for write access — and that was wrong.
  App Store upload rejects the build with **90683** regardless: altool's static check looks at the
  *entitlement*, not at which APIs you call, and `com.apple.developer.healthkit` permits writing.
  Its own words: "or the app has one or more entitlements that permit such access". There is no
  read-only HealthKit entitlement to opt down to, so the string is mandatory for anyone reading
  health data at all. It is present now, and says Heart does not write — truthful, and never shown
  to a user, since the sheet only surfaces it when write access is requested.

  That pairing was briefly wrong in a way only running the app revealed. `requestAuthorization`
  defaults to `READ_WRITE` when `permissions` is omitted, so the sheet read *"would like to access
  **and update** your Health data"* — asking for write we have no code to use, while declaring no
  update usage string to justify it. iOS is documented to terminate an app that requests HealthKit
  access without the matching usage description, so this was a latent crash as well as an
  over-reach. `requestAccess` now passes `HealthDataAccess.READ` for every type. Tier 1 widens it
  deliberately, and only for the workout type it actually writes — at which point the update string
  stops being a formality, starts being shown to users, and has to be rewritten to describe what
  Heart actually saves.
- **Privacy policy** — required for HealthKit regardless. Now a much easier document to write.
- **Apple 5.1.3** — forbids health data for advertising or data mining, forbids third-party
  disclosure without consent, forbids iCloud storage. Device-only satisfies all of it by
  construction.
- **Google Play health declaration** — Tier 2 only, weeks of lead time, start early.

## 8. Testing reality

| Target | Emulator | Notes |
|---|---|---|
| HealthKit read/write | Simulator works, store is empty | Seed the app's own `health_samples` table directly rather than the OS store — see below. Don't count on entering data through a Health UI on the simulator. |
| Health Connect | Android emulator, API 34+ | In the OS from Android 14; older emulators need the standalone APK. Sample data can be written programmatically. |
| BLE chest strap | No emulator | Physical strap only. |

**Seeding without HealthKit.** Writing rows straight into `health_samples` in the simulator's
`heart.db` beats faking `HealthService`: the app's own reconciliation SQL still does the
aggregating, so what renders is what migration 0009 and `dailyCumulativeHealth` actually produce.
Ninety days across the six metrics, with steps written from *two* sources covering the same days,
is enough to see the card layout and to settle the question below.

**And it did settle part of it.** Seeded so that a naive `SUM` would report 10,984 steps for a day
where the best-covered source saw 6,780, the card showed **6,780**. The per-source reconciliation
is doing what it was written to do, on a device, through the real query — which was the one claim
in this feature that no unit test could close.

Deduplication and multi-source behaviour are the parts that will not show up in a simulator with
hand-seeded data — they need a real phone with a real watch and a couple of years of accumulated
samples. Which we have.

**Photographing the states.** Build the driver entrypoint for the simulator, install and launch it
with `simctl`, read the VM service URI out of `simctl spawn <udid> log show --predicate 'process ==
"Runner"'`, and drive it with a plain `FlutterDriver.connect` script — the run configs are not
involved and neither is DTD. Two things cost time on 2026-08-15:

- The iPhone 16 simulator's HealthKit holds a body-mass sample, so **the dormant state cannot be
  reached by emptying `health_samples`** — the next sync reads it straight back. `simctl privacy`
  has no `health` service either. Forcing `metrics` empty for one build is the cheap way in.
- `FlutterDriver` has no `setFrameSync`; it is `runUnsynchronized`. Screenshots come back as PNG
  bytes from `driver.screenshot()` and contain no status bar, which is fine for judging layout.

## 9. Order

1. **Tier 0** — read HealthKit, store with source, chart it. Starts the collection clock for Tier 4.
2. **Tier 1** — write workouts back. Days, and users notice immediately.
3. **The device-only copy and the two leak paths (§6)** — before the feature is visible, not after.
4. **Unblock body-metric goals** — body mass now arrives from Tier 0, and the goals doc has already
   designed where it lands.
5. **Tier 2** — Health Connect. Start the Play paperwork in parallel with step 1.
6. **BLE straps** — prototype; it is the cheap answer to live in-set HR.
7. Weather, Wear OS, watch app: opportunistic, and only on evidence.
