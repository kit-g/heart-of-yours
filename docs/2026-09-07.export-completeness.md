# The export completeness check

The app half of heart-api#75 (`GET /accounts/summary`). Before the export page offers a file, it
asks the account what it holds and compares that against the mirror the file will be written
from. This page is what is compared, what deliberately is not, and the one reuse of the endpoint
that looks obvious and is wrong.

## The gap

The export writes from the local store, not the API — that is the right shape (it works offline,
and it is the only shape the device-only health rule permits), but it has a hole: **the app had
no way to know the mirror was whole.** An interrupted sync, a fresh install, a replay that
stopped half way through the anonymous → account upsync — in each case the store is a *prefix* of
the account and the file is silently partial. A partial export looks exactly like a complete one.

What stood in for the check was `hasMoreHistory` (`Workouts`), the history list's pagination
flag. It covers workouts and nothing else, and it can only say "there is more", never how much —
so the page's line was *"Includes the 118 workouts on this phone"*, with no second number in it.
It is still the fallback when the account cannot be asked, and nothing more than that.

## What is compared

Both sides answer in the same shape, an `AccountSummary` of `{count, latestId}` per collection,
so the comparison is a comparison and not a translation:

| Side | Where |
|---|---|
| The account | `Api.getAccountSummary` → `GET /v1/accounts/summary` |
| The mirror | `LocalDatabase.mirrorSummary` (`shared/heart_db/lib/src/parts/mirror.dart`) |
| The compare | `DataExport.completeness` (`shared/heart_state/lib/src/export.dart`) |

Five collections, and the database is the one that decides which — `completeness` walks whatever
`mirrorSummary` reports rather than keeping a second list that could drift from it.

| Collection | Counted as |
|---|---|
| `customExercises` | `exercises` where `own = 1` |
| `templateFolders` | `template_folders` |
| `templates` | `templates` with a name — an unnamed draft is a local state the server never sees |
| `workouts` | `workouts` with an `end` — a workout still running is not one either |
| `goals` | `goals`, archived included: the account still holds them |

The other five the server reports stay out, because absent is honest and zero is not. A zero on
this side would read as *"the server has rows I am missing"* when it means *"this device does not
keep that"*: `templateShares`, `comments` and `connections` are coach features the app has not
shipped, `workoutImages` are S3 rows the file does not carry, and `exercisePreferences` is the
awkward one — the server keeps unit, rest timer and chart type in one table, while the app
spreads the same data across `exercise_details` and `charts` and holds no preference row ids at
all, so it has neither a comparable count nor a head.

### A count and a head, not just a count

Two stores can hold the same *number* of rows and not the same rows. Ids are uuid v7, so the
newest id is also the high-water mark, and a matching count over a different head is a divergence
the count alone reads as in sync. `MirrorGap.diverged` carries that case.

A device holding **more** than the account is not a gap: those rows are in the file either way,
and getting them onto the account is the upsync's business, not this page's.

## Three states, not two

`completeness` answers `List<MirrorGap>?`, and the nullable is the point:

- `[]` — measured, and the mirror is whole. The page says nothing.
- `null` — the question could not be asked. The page falls back to `hasMoreHistory`.
- non-empty — the measured shortfall.

`Api.getAccountSummary` throws rather than falling back to an empty summary for the same reason.
An empty summary is a *claim* — "the account holds nothing" — and it reads as "your mirror is
complete", which is the one answer a failed call must never give.

## The copy

One line spells out numbers, and only for workouts: it is the collection that is routinely a
prefix, the only one with somewhere for the user to go ("open History and scroll back"), and the
only shortfall a number makes concrete. Everything else — including a divergence in workouts — is
one general line, because *"3 of your 5 folders"* is noise rather than an action.

## What this must not be used for

Two reuses suggest themselves once the numbers are on hand. Both are wrong, for the same reason:
**counts and heads cannot see an edit or a deletion.**

- **Short-circuiting the launch pulls.** Skipping `GET /templates` because the counts and heads
  match would pin stale rows in place — a renamed template or an edited workout leaves both
  numbers identical.
- **Skipping rows in the upsync replay** (`docs/2026-09-06.upsync.md`, finding 4: an account with
  an earlier mirror replays its own rows as `200`s, one request each). A head only proves
  "nothing here is newer than the server's newest". A row created on this phone while the remote
  leg was closed, on an account that got a newer row from another device meanwhile, sits *below*
  the head — it would be skipped and never backed up. The replay is chatty but correct by
  construction; a `synced` flag on those tables is the exact fix, and this is a heuristic.

The advisory line on the export page is the safe use precisely because a wrong answer makes a
sentence wrong, not a file.

## Gaps

- **Counts, not checksums.** Two stores agreeing on count and head can still disagree in the
  middle. Catching that needs a per-collection digest; the working assumption, the server's too,
  is that a truncated sync is the failure that happens.
- **No child rollups.** `workouts` counts workout rows, not their exercises or sets. The app only
  ever writes whole workouts, so the header count stands in for the tree.
- **One read, when the page opens.** It is not refreshed while the page is up, and there is no
  retry — the fallback line covers a refusal. Nothing polls it.
- **`exercisePreferences` cannot be compared from this side.** Closing that would mean either the
  app keeping preference row ids or the server exposing a shape the app's split storage can be
  counted into. Worth raising on heart-api if the preferences mirror (#109) ever looks suspect.
