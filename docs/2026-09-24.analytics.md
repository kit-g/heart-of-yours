# Analytics: the event taxonomy

What the app reports to Firebase Analytics, what it may never report, and where each event is
emitted from. The vocabulary lives in one class — `Analytics` in `shared/heart_state` — so the
wire names are decided in one place and a rename is an edit rather than a grep.

All three tiers ship: the ladder funnel, the habit loop, and feature reach.

## Three rules

**1. Health data never reaches an event.** Nothing derived from a `HealthMetric` —
`heartRate`, `heartRateVariability`, `restingHeartRate`, `bodyMass`, `bodyFatPercentage` — is a
legal argument to any `Analytics` method, as value, bucket or flag. Not even a boolean saying
whether a metric is tracked. See `docs/2026-09-05.health-data.md`; the same reasoning that keeps
a sqflite error message out of Sentry keeps a bucket out of GA4.

**2. Identifiers, never copy.** An event carries `provider: "google"`, never a localized exercise
name, a workout title, a folder name or a note. Error **codes** are identifiers and are fine; an
exception *message* is copy and may carry an address. This is the same rule the data classes
follow (`docs/style.md`, *Copy*).

**3. Nothing is awaited, nothing throws.** Reporting must never slow down or break the thing it
reports on. `Analytics` swallows transport failures into `onError`; anything that *computes* an
argument from an SDK object guards itself the same way (`Auth._isNewAccount`).

## What GA4 will and will not hold

- Event names: ≤ 40 characters, letters, digits, underscores. The `firebase_`, `google_` and
  `ga_` prefixes are reserved. 500 distinct names per app.
- Parameters: 25 per event, values ≤ 100 characters.
- **Parameter values are `String` or `num` only.** The SDK asserts on anything else, so
  `Analytics` encodes: a bool goes as `"true"`/`"false"`, not 1/0, because these read as
  registered custom *dimensions* and a dimension breakdown is what the questions want.
- User properties: 25 per project, names ≤ 24 characters, values ≤ 36.
- **A parameter that is not registered as a custom dimension in the console is collected and not
  reportable.** 50 custom dimensions, 50 custom metrics. This is the trap.
- No uid, no email, ever — GA4 forbids it and the app-instance id already exists.

`screen_view` is not in this taxonomy: `FirebaseAnalyticsObserver` (`main.dart`) already sends it
on every route change.

## Verifying that an event actually arrived

Three things have to line up, and each one has silently swallowed a verification attempt:

1. **The run has to report at all.** A debug build sends nothing; force it with
   `--dart-define=HEART_FORCE_TELEMETRY=true` (`lib/core/env/telemetry.dart`), which lifts the
   debug rule for Sentry, Analytics and the HTTP wrapper together and still never lifts the Test
   Lab exclusion.
2. **The project has to be linked to a GA4 property.** `scripts/ga4.py --env <env> properties`
   says so in its first line. Prod was unlinked until 2026-09-25, and an unlinked project
   uploads into nothing without erroring.
3. **The app has to background before the events upload.** This is the one that looks like a
   bug and is not. Firebase on iOS sends the startup burst promptly — `first_open`,
   `session_start`, and anything logged during launch — but an event logged later in a
   foreground session waits for the next upload window, which a background transition triggers.
   `flutter drive` kills the app without ever backgrounding it, so workout events sat unsent
   through four separate attempts, including with `--keep-app-running`. Background the
   simulator app (launching any other app does it) and the queue flushes within a minute.

Then `scripts/ga4.py --env dev realtime` shows them. Use `realtime`, not `events`: the date-range
reports lag by hours, and a freshly sent event is genuinely absent from them for a while.

## Which runs report

A debug build, a `flutter_driver` run and Firebase Test Lab report nothing. `initAnalytics`
(`lib/core/env/analytics.dart`) returns a `SilentAnalyticsService` *and* calls
`setAnalyticsCollectionEnabled(false)` — both halves are needed, because the second is what stops
the observer's own `screen_view` from counting a robot's navigation as a session. The exclusion
list is shared with Sentry (`lib/core/env/telemetry.dart`): a run worth excluding from one is
worth excluding from the other.

This is a change of behaviour from before Tier 1: debug runs used to report screen views.

## User properties

| Property           | Values                                     | Set from                                                    |
|--------------------|--------------------------------------------|-------------------------------------------------------------|
| `account_state`    | `anonymous` / `account` / null             | `Auth._adopt`                                               |
| `auth_provider`    | `google` / `apple` / `password` / null     | `Auth._adopt`, off `providerData.first`                     |
| `form_factor`      | `phone` / `tablet`                         | `main.dart`, the same measurement the orientation lock uses |
| `workouts_bucket`  | `0` / `1_3` / `4_10` / `11_30` / `31_plus` | `Backfill._run`, off the server's own count                 |
| `templates_bucket` | same buckets                               | `Templates.init`, the user's own templates only             |

Null is meaningful in the first two: no session at all is neither rung, and saying so beats
leaving the last session's answer standing against the next one's events.

Bucketed because a raw count makes a terrible user property: every distinct value becomes its own
segment, and "users who have logged 37 workouts" is a cohort of one. `workouts_bucket` uses the
account summary the backfill already fetches — the mirror holds only the newest page, so counting
it would put a 200-workout user in `11_30`. `templates_bucket` excludes the samples, which every
account has.

`health_connected` was considered and left out. It is arguably integration metadata rather than a
health reading, but it is not worth the argument.

## Tier 1 — the ladder funnel

| Event                    | Parameters                                                     | Emitted from                                                             |
|--------------------------|----------------------------------------------------------------|--------------------------------------------------------------------------|
| `anon_session_minted`    | —                                                              | `Auth._mintAnonymous`                                                    |
| `signup_started`         | `provider`, `from_anonymous`                                   | `Auth.loginWithGoogle` / `loginWithApple` / `signUpWithEmailAndPassword` |
| `signup_completed`       | `provider`, `arrival`                                          | `Auth._reportArrival`, on Firebase's `isNewUser`                         |
| `login_completed`        | `provider`, `arrival`                                          | same                                                                     |
| `signup_failed`          | `provider`, `reason`                                           | `Auth._reportFailure`                                                    |
| `upsync_replay_finished` | `rows`, `uploaded`, `existing`, `skipped`, `duration_ms`, `ok` | `Upsync._reportReplay`                                                   |
| `deletion_scheduled`     | —                                                              | `Auth.scheduleAccountForDeletion`                                        |
| `deletion_cancelled`     | —                                                              | `Auth.deleteAccountDeletionSchedule`                                     |

`signup_prompt_shown` (`placement`) exists on `Analytics` and has no call site yet: it belongs to
whichever surface offers an account, and is wired when that surface is next touched.

### `arrival`, the dimension this tier is for

`AccountArrival` — `linked`, `takeover`, `moved`, `direct`. It is the one thing only `Auth._linkOrSignIn`
knows, because by the time anything downstream looks, both anonymous paths are an account with a
replay owed:

- **`linked`** — the credential was new, `linkWithCredential` succeeded, the uid survived and the
  store was already the account's.
- **`takeover`** — the credential already had an account (`credential-already-in-use`, or an email
  *login*), so the session signed into it and `Upsync.claim` rekeyed every local row onto the new
  uid first. Nothing is lost; it is the slow path, and the one that meets the server's own copy of
  rows it is about to re-offer — the "3 uploaded, 23 already there" `Upsync.adopt` documents.
- **`moved`** — a *new* account signed into directly from the anonymous session instead of linked
  onto it: Apple, whose identity token Firebase redeems once, so it is never spent on a link
  first. The uid changed, so `Upsync.claim` rekeyed the rows as for a `takeover`, but the server
  has none of them yet.
- **`direct`** — no anonymous session stood behind it. A third answer, not a quiet `takeover`.

### What is deliberately not counted

Backing out of a sign-in sheet is not a failure (`Auth._isCancellation`). It is the most common
way any of these ends, and counting it would make `signup_failed` mostly cancellations with the
real errors a rounding error inside. `signup_started` still fires, so the abandonment is visible
as a funnel drop, which is what it is.

## Tier 2 — the habit loop

| Event                     | Parameters                                                               | Emitted from                                                 |
|---------------------------|--------------------------------------------------------------------------|--------------------------------------------------------------|
| `workout_started`         | `source`, `pinned_notes`                                                 | `Workouts.startWorkout`                                      |
| `workout_finished`        | `source`, `exercise_count`, `set_count`, `duration_min`, `unticked_sets` | `Workouts._reportFinished`                                   |
| `workout_cancelled`       | `had_content`, `exercise_count`                                          | `Workouts.cancelActiveWorkout`                               |
| `workout_edited`          | `field`: `times` / `sets`                                                | `Workouts.editWorkout`, `editWorkoutTimes`                   |
| `template_created`        | `source`: `editor` / `from_workout` / `duplicate`                        | `Templates.saveEditable` (when `local`), `workoutToTemplate`, `duplicate` |
| `template_folder_created` | —                                                                        | `Templates.createFolder`                                     |
| `template_moved`          | `filed`                                                                  | `Templates.moveToFolder`                                     |
| `exercise_created`        | —                                                                        | `Exercises.makeExercise`                                     |
| `history_backfilled`      | `pages`                                                                  | `Backfill._run`, only when it actually paged                 |

`WorkoutSource` is `blank`, `template`, `sample` or `repeat`, and it is **stated by the caller**,
not inferred: all four arrive at `startWorkout` as a `Workout`, and only the surface that offered
it knows which it was. The sample grid and the start dialog tell themselves apart by
`allowsEditing`, which is false only for samples. A workout restored from the store on launch has
no answer and reports `blank`.

Two measurement traps, both of which this code is shaped around:

- **`workout_finished` is counted after `saveWorkout`, not before.** That method opens with
  `removeEmptySets`, which drops every set the user never ticked and then any exercise left
  holding none — so what survives is the workout that is stored and shown in history.
  Counting first would report a template's fifteen prescribed sets for someone who ticked three,
  which is the exact confusion `Workouts._edited` exists to prevent. What was set up and
  abandoned is `unticked_sets`' job, and that is counted before the prune.
- **`workout_cancelled` is counted before the teardown**, because the workout is about to be
  removed from `_workouts` and reading after gives zero for everything.

`duration_min` is the time trained: `Workout.duration`, which is `end − start` less every pause
(#134). A workout paused for twenty minutes reports twenty minutes fewer than its wall-clock span,
and one finished at its last set from the idle offer reports up to that set. Builds from before
pauses sent the wall-clock span; for a workout never paused the two agree.

### The health boundary

`set_count`, `exercise_count` and `duration_min` are what the user typed into this app. Rule 1
covers what is *read from* the health store, and none of these is. Sets are written *back* to
HealthKit, so if the rule is ever read as "anything that touches the boundary in either
direction", these become buckets or disappear — but no value ever ships, only counts.

## Tier 3 — feature reach

| Event                            | Parameters                    | Emitted from                                                 |
|----------------------------------|-------------------------------|--------------------------------------------------------------|
| `data_exported`                  | `format`: `json` / `csv`      | `export_data.dart`                                           |
| `data_imported`                  | `source`, `unmatched`, `created_custom` | `import_data.dart`                                           |
| `avatar_updated`                 | —                             | `Auth.updateAvatar`, on the way in                           |
| `upgrade_gate_shown`             | —                             | `main.dart`, beside `requireUpgrade`                         |
| `notification_permission_result` | `granted`                     | `ensureNotificationPermission`, only when a prompt was shown |
| `watch_app_switched`             | `on`, `from_watch`            | `WatchPresenter` (the first watch launch), Settings switch   |
| `set_type_changed`               | `set_type`                    | the set type menu (`set_type.dart`), all three editors       |
| `feature_linked`                 | `feature`, `source`           | the Features page, opened at one feature                     |
| `api_token_created`              | `purpose`, `expiry`           | the new-token page (`api_tokens.dart`), on a `201`           |
| `api_token_revoked`              | —                             | the tokens page, after the server took the revoke            |
| `sign_in_connected`              | `provider`                    | Account control's Connect, and a refused sign-in's catch-up  |
| `sign_in_disconnected`           | `provider`                    | Account control's Disconnect                                 |

`avatar_updated` fires on entry rather than on success on purpose: the 404 that broke avatar
upload on prod was invisible precisely because nothing counted attempts.

`watch_app_switched` with `from_watch: true` is the watch app's opt-in (#175): opening Heart on the
watch for the first time is the yes, so that is the only event that feature's reach has. It fires
once — later launches find the question already answered.

`set_type_changed` carries the type picked, so `set_type: normal` is a set made plain again. It
fires from the menu rather than from `Workouts`, because templates and the history editor own
their sets without it.

`feature_linked` fires once per arrival at the Features page with a feature to show (#239):
`source: whats_new` from a note's button, `source: link` from a universal link — a post, a
tutorial, the website. It does not say whether the switch was then flipped; the feature's own
reach answers that.

`notification_permission_result` skips the already-granted path. That is not a decision, and
counting it would report a near-100% grant rate for a dialog nobody saw.

`data_imported` carries the gap between `unmatched` and `created_custom` — the consent step being
declined is the only part of that flow that can lose data. `source` is the app the export came
from (`strong` / `hevy`); a Hevy file the server parks for a manual import never reaches the
commit, so it is not counted.

**`language_changed` was dropped.** There is no in-app language picker; the app follows the
device locale, which GA4 already reports as a dimension of its own. An event with no possible
trigger is dead code.

**Goals are absent on purpose**: health-metric goals are local-only, and one `goal_set` event
firing for both kinds would leak which metric someone tracks. Workout-goals-only, named as such,
or not at all.

## Registration, and the console work left

1. Custom dimensions and metrics are registered by `scripts/ga4.py --env <env> dimensions
   --apply`, not by hand: it diffs the property against the taxonomy and creates what is
   missing, so a new parameter is re-registered by re-running it. Both properties are current.
   Adding a parameter to `Analytics` means adding a row to that script's tables, or it is
   collected and never reportable — which looks exactly like the app not sending it.
2. Mark `signup_completed` and `workout_finished` as conversions.
3. Define an audience for "anonymous, `workouts_bucket` of `4_10` or better" — both the cohort
   worth prompting for an account and the trigger In-App Messaging would need later.
