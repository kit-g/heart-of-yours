# Accessibility

The app is checked against Flutter's built-in accessibility guidelines by
`test/a11y_test.dart`, which pumps real screens through the app harness and
runs `meetsGuideline` against them. It is picked up automatically by
`make test-app` / CI — no separate command to remember.

## The matrix

`test/a11y_test.dart` sweeps a screen × guideline matrix (`_matrix`): every
`(_Screen, _Guideline, String? reason)` triple becomes one `testWidgets`.
`reason == null` means the combination is enabled and must keep passing.
A non-null `reason` skips the test and prints the reason in `flutter test`'s
output, so debt is enumerable instead of silently missing — `flutter test`
tells you both what's covered and what still owes a fix, with enough context
(file:line, the constraint blocking it) to act on later.

**Guidelines checked, per screen:**
- `labeledTapTargetGuideline` — every tappable control has a label a screen
  reader can announce.
- `textContrastGuideline`, twice — once against the light color scheme, once
  against dark (`_Guideline.textContrastLight` / `.textContrastDark`). Both
  run the same Flutter constant; the test flips `AppTheme.toDark()` on the
  live widget tree before the second one. Static analysis can't do this: the
  color scheme is seed-derived at runtime (`app.dart:227`).
- `androidTapTargetGuideline` / `iOSTapTargetGuideline` — minimum tap target
  size for each platform's HIG.

## Enabling an entry

1. Fix the underlying issue.
2. Flip that row's `reason` to `null` in `_matrix`.
3. Run `flutter test test/a11y_test.dart` and confirm it's green.

Don't delete a failing row instead of skipping it — a missing combination
reads as "covered," a skipped one reads as "known, here's why." If a fix
also closes a *different* screen's version of the same issue (e.g. the
nav-bar contrast reason repeated across every bottom-nav screen), flip all
of them together.

## Adding a screen or guideline

Add cases to the `_Screen`/`_Guideline` enums, wire the new screen into
`pumpTo` (usually a couple of taps by `AppKeys`, mirroring
`test/router_test.dart`), and add its five rows to `_matrix`. Give every new
row an explicit `null` or a reason — there's no implicit default.

## Patterns

**Labeled, correctly-sized icon button** —
`lib/presentation/widgets/health/section.dart:205-217`: a `tooltip` from
`L.of(context)` plus explicit 44×44 constraints. `IconButton.tooltip` is both
the accessibility label and the visible long-press hint, so it's usually the
whole fix.

**Icon-only overflow menu** — pass `tooltip:` to `PopupMenuButton` the same
way (`lib/presentation/routes/history/workout_item.dart`,
`lib/presentation/routes/workout/templates.dart`,
`lib/presentation/routes/workout/card.dart`).

**Bare `GestureDetector`/`InkWell`** — these render as their child (often
plain text or an image) and get no button semantics for free. Wrap in
`Semantics(button: true, label: …)`:

```dart
Semantics(
  button: true,
  label: L.of(context).clearSearchTooltip,
  child: GestureDetector(onTap: onClear, child: const Icon(Icons.close_rounded)),
)
```

If the wrapped subtree also exposes its own redundant text (e.g. a duration
formatted both into the `Semantics.label` and into a child `Text`), add
`excludeSemantics: true` so a screen reader doesn't announce it twice — see
`lib/presentation/widgets/duration_picker.dart`'s `_Item`.

**A `TextField` with no visible label** — the app's fixed-height number
entry fields (`lib/presentation/widgets/workout/text_field_button.dart`) use
`InputDecoration.collapsed` with a `-` placeholder on purpose (adding a
`labelText` would grow the field). Wrap the field in `Semantics(label: …,
textField: true)` instead of changing the decoration:

```dart
Semantics(
  label: semanticLabel, // e.g. L.of(context).reps
  textField: true,
  child: TextField(decoration: const InputDecoration.collapsed(hintText: '-'), ...),
)
```

**Images** — `AppImage` (`lib/presentation/widgets/image.dart`) takes a
`semanticLabel`. Pass one for every image that carries information (a
progress photo, an exercise thumbnail); leave it `null` for a genuinely
decorative image (an avatar sitting next to a name, where the surrounding
`Semantics(button: true, label: …)` already describes the tap target) —
`AppImage` excludes an unlabeled image from the semantics tree rather than
announcing nothing useful.

**A `CustomPaint` that draws data with no text equivalent** — a screen
reader cannot perceive a painted chart or progress bar. Wrap it in a single
`Semantics(label: …)` that states the same thing as a sentence: what it
measures, the range, and the current/latest value. Summary-level, not
per-point — see `lib/presentation/widgets/goals/ladder_bar.dart`
(`GoalLadderBar.semanticLabel`, built by its caller in
`lib/presentation/widgets/goals/row.dart` from the same pieces already used
for the visible status line) and `lib/presentation/widgets/exercise_chart.dart`
(`_dataChart`'s `Semantics` wrapper around `HistoryChart`).

**A live-updating value (a timer)** — wrap the region in `Semantics(label:
…, liveRegion: true, excludeSemantics: true)`, rebuilding it as the value
ticks so the label stays current. See the rest-timer ring in
`lib/presentation/widgets/countdown.dart`.

## The rule: semantic labels are translated copy

Every string that reaches `Semantics.label`, `IconButton.tooltip`, or
`AppImage.semanticLabel` is user-facing text and goes through
`shared/heart_language` like any other copy in the app — see the
`translations` skill. Never hardcode an English string into a `Semantics` or
`tooltip` argument, even for something that feels like debug/dev text. The
one pre-existing exception this ticket fixed
(`lib/presentation/widgets/workout/empty_state.dart`'s `'Empty workout'`
literal) was itself a bug, not a precedent.

## Known debt

Guideline failures found but intentionally left unfixed — each needs either
a visual/layout change (tap-target sizing, theme contrast) or product/design
input (drag-and-drop or swipe-to-delete alternatives) that's out of scope
for this pass. They're enumerated as skipped `_matrix` entries with reasons;
see those reasons for specifics, and the ticket's closing report for the
full list with file:line references.
