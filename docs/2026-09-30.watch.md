# The watch app — how it fits together

Heart on Apple Watch (#175) is a **remote for the workout the phone is running**. This page is the
map: which piece does what, on which device, and where to look when something misbehaves. The
tickets and decisions behind it are #187, #182–#186 and the research comments on #175.

## The one rule

**The phone is the only writer.** The watch holds no workout of its own — only the last state the
phone sent it. A tap on the watch is a *request*; the phone applies it through the same `Workouts`
calls a tap on the phone makes, and the watch learns the outcome from the next state it is sent.
Nothing on the watch ever edits a workout, and there is nothing on it to sync, sign in to, or lose.

This is the design the #175 research pointed at: the failures people report in other apps' watch
apps — lost sets, duplicate workouts, "unreachable", login walls — come from keeping two live copies
of the workout. Heart keeps one.

| File | Device | Job |
|---|---|---|
| `lib/core/env/watch.dart` | phone, Dart | The vocabulary: `WatchState` (what the watch shows), `WatchCommand` (what the user did), `WatchLink` (the channel). |
| `lib/presentation/navigation/watch.dart` | phone, Dart | `WatchPresenter`: builds the state from `Workouts`/`Alarms` as finished copy, sends it only when it changes, applies commands, handles the opt-in. |
| `ios/Runner/WatchChannel.swift` | phone, native | Forwards Dart's state to the watch as WatchConnectivity's application context, and the watch's commands to Dart. Reads neither. Keeps what arrives while Dart isn't listening. |
| `ios/Runner/MirroredWorkout.swift` | phone, native | Accepts the watch's mirrored Health session. Holding it is the point: iOS keeps Heart running while it's live. Nothing is read from it. |
| `ios/Watch/PhoneSession.swift` | watch | The watch's end of the connection: the phone's last state, the commands it has not answered yet, and what to show — the one with the other applied on top (#206). |
| `ios/Watch/WatchState.swift` | watch | Decodes a state. Every string in it is finished copy from Dart. |
| `ios/Watch/WorkoutView.swift` | watch | The screen: workout, rest countdown, set controls, value editor, Finish, Always-On. |
| `ios/Watch/WorkoutSession.swift` | watch | The HealthKit workout session: heart rate and energy on the wrist, the rest-over tap, and the one workout saved to Health on finish. |
| `ios/WatchWidgets/` | watch | The complication. Reads a small snapshot the watch app leaves in the shared app group. |
| `ios/WatchUITests/` | Mac | XCUITest steps that drive the watch app on a simulator (tap, Digital Crown). Not a CI suite. |

## What travels, and how

**Phone → watch: one state, the whole picture.** `WatchWorkout` (the workout, the set up next with its
values in the unit the phone shows, every set of every exercise for the watch's second page, and the
copy for every control), or `WatchMessage` (idle, off).
Sent as the application context — the latest wins, and it reaches a watch app that isn't running —
plus a direct message when the watch is on screen, so it updates at once.

**Watch → phone: commands.** `complete` (a set, with the values shown), `edit` and
`untick` (a set already done, gone back to from the workout page), `adjustRest`, `skipRest`,
`finish`. Adding sets or exercises stays a phone job. Each names its workout and set, and carries
when it happened; one that no longer matches is dropped and answered with the current state.

**Phone in the locker (#206).** The watch applies every command to the phone's last state at once
(`WatchState.applying` mirrors the phone's moves, including `upNextIn`'s rule for the next set), and
the phone's next state replaces it: the phone is still the only writer. In reach a command goes as a
message; out of reach, or when a message fails, it goes as user info, which the system holds and
delivers in order once the phone is back, even to a phone app that isn't running. To make that work,
every set row carries its own copy ("Set 2 of 3", last time, the "Next:" line) and every exercise
its rest length. On the phone, a replayed tick starts only what is left of its rest, and a replayed
Finish ends the workout when it was confirmed, not when it arrived. A queued Finish ends the watch's
workout session on the spot; one sent in reach waits for the phone to accept it.

**Copy.** The watch translates nothing. Dart sends every string, already localised. Before the
phone has said anything, the watch shows an iPhone symbol — a picture, because there is no copy yet
to say anything with.

## The opt-in

`Feature.watchApp` in the #138 framework (`docs/opt-in.md`). Opening Heart on the watch for the first
time is the yes: the watch tells the phone "opened", and the phone turns the feature on if it was
never answered. Until then the phone sends nothing. Off, the watch shows "Turned off in Heart on your
iPhone". The switch lives in Settings › Features and appears only when a paired watch has Heart.

## Health

Only while Heart is on screen on the watch during a workout does it start a Health workout session —
never on its own, because only one app can run one and starting Heart's ends Apple's Workout. The
readings stay on the watch and in Health; a finished workout is saved once, by the watch, and the
phone skips its own write (`WatchLink.finish`). A cancelled one is discarded. The policy is
`docs/2026-09-05.health-data.md`, *The watch app*.

## Environments

The watch has none of its own. Each build configuration sets `HOST_BUNDLE_IDENTIFIER` to Runner's
bundle id, and everything watch-side derives from it: `…watchkitapp`, `…watchkitapp.widgets`,
`group.…`, the name and icon. A dev phone build carries a dev watch app, which talks only to the dev
phone app. Schemes `watch-dev` / `watch-prod` build the watch alone.

## When it misbehaves

| Symptom | Look at |
|---|---|
| Watch stuck on the iPhone symbol | The phone never sent a state: the feature is unanswered or the phone doesn't see the watch app as installed (`WCSession.isWatchAppInstalled`). A watch app installed by `devicectl` rather than through the iPhone's Watch app may not count. |
| A tap spins, then nothing | The phone dropped the command as stale (the set changed) — the next state is the truth. Or the phone app couldn't be woken: `WatchChannel` keeps the command and Dart applies it at the next launch. |
| Values on the phone don't match the watch | `set_item.dart`'s `_syncFromSet` — rows follow their set when it changes underneath them. |
| No heart rate | Health access declined on the watch (asked once), or Heart wasn't on screen when the workout started. |
| Two workouts in Health | The phone didn't learn the watch measured: `watch.measuring` in the phone's `UserDefaults`, set by the watch's "measuring" message. |

Driving it on simulators: `ios/WatchUITests/WatchUITests.swift`. Its header has the command, and the
one thing no test can reach — Health's permission sheet on the watch, which has to be tapped by hand.

Building it: Xcode refuses a scheme that embeds a watch app unless the watchOS platform is installed
(`xcodebuild -downloadPlatform watchOS`), even for a device archive; CI does this when it has to.
Installing to a watch from Xcode needs an Xcode that supports the watch's watchOS; when it doesn't,
install through the iPhone's Watch app from a phone build.
