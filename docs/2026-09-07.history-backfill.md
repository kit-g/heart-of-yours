# Keeping the mirror whole

heart-of-yours#113, the app half of heart-api#75. The account's history is paged, the app computes
off the local mirror, and until this the two were allowed to disagree. This page is why that was a
correctness bug rather than a display one, how the backfill fixes it, and the one thing the summary
endpoint must never be used for.

## The bug

`Workouts.initHistory` asks for the newest page with no `since`, so every launch re-fetches the same
newest twenty. Nothing else ever fills the middle — only the user scrolling History does. The mirror
is therefore a *prefix* of the account, indefinitely, and these all read the mirror:

| Reads the mirror                        | Through                                                                                |
|-----------------------------------------|----------------------------------------------------------------------------------------|
| *Workouts per week*                     | `Stats.getWorkoutSummary` → local SQL                                                  |
| Goal progress                           | `workoutCounter` (`lib/core/utils/goals.dart`) → `getWeekly/Monthly/TotalWorkoutCount` |
| Exercise charts, records, previous sets | `ExerciseHistoryService`, `PreviousExercises`                                          |
| The data export                         | `DataExport.read`                                                                      |

A "4 workouts per week" goal on a device holding 20 of 568 workouts is not drawn wrong; it is
answered wrong. Nothing told the user, and nothing told the app.

The first pass at this shipped a line on the export page — *"Includes 20 of your 568 workouts…
open History and scroll back to fetch them first"* — which is the app handing the user its own
bookkeeping. That string and its two siblings are gone.

## The backfill

`Backfill` (`shared/heart_state/lib/src/backfill.dart`), the pull counterpart of `Upsync`. After
`initHistory`, it pages the rest of the account's history down in the background, once per account
per device, and records that it did. Resumable for free: the keyset cursor comes off each page and
pages already land in the store, so an interrupted run restarts where it stopped.

It shares `Workouts`' cursor through `backfillPage()` — the same fetch, store and absorb
`loadMoreHistory` does, *without* `loadingMoreHistory`. That flag puts a spinner on History's tail,
and a page nobody asked for must not look like one the user is waiting on.

### The mark decides, not the endpoint

`GET /accounts/summary` is not polled. `syncs` carries `history_backfill:<uid>`, the same watermark
shape the health backfill uses, and it is the whole decision:

| Launch                             | Requests                                                     |
|------------------------------------|--------------------------------------------------------------|
| Marked uid                         | **0** — the mirror is whole; only the normal delta pull runs |
| Unmarked uid, mirror already whole | **1** — settles the mark, pages nothing                      |
| Unmarked uid, mirror short         | **1**, plus one per page                                     |

The single call answers both questions at once: *is this device short?* and *short of what?* — the
second being the total the row counts towards. An install upgrading into this version with a mirror
that happens to be complete settles on that one request and never pages.

The mark is written only when the count says the mirror is the account. `hasMore: false` proves
paging finished, not that every row landed — a page that failed to store, a row deleted between
pages — so the run recounts at the end and leaves the mark off if the numbers disagree. The next
launch then tries again. `eraseUser` drops it with the rows.

If the summary call itself fails, the run still goes ahead on `hasMore` alone; it only costs the row
its numbers.

### What the user sees

`BackfillRow`, in the profile's sliver list beside `UpsyncRow` and built from the same primitives: a
line and a bar while it runs, a line and a **Retry** when the server could not be reached.

```
┌──────────────────────────────────────┐
│ Restoring your history…    120 of 568│
│ ▓▓▓▓▓▓▓▓░░░░░░░░░░░░░░░░░░░░░        │
└──────────────────────────────────────┘
```

**No finished line.** The user never asked for this sync, and announcing the end of a job they did
not start is a notice about the app's bookkeeping. The row simply goes.

### Ordering

`Backfill` sits above `Upsync` in `HeartApp`'s providers, because `Upsync.onComplete` reaches it
through `_resync` and a provider's `create` context only sees what is declared above it. It waits
for a replay through `RemoteAccess` instead — `allowed` is `account && !replaying`, so an anonymous
session never starts one and a running replay owns the wire until it is done.

`_initTrainingData` runs the aggregations twice: once off whatever the mirror holds, so the profile
is not blank, and again after the backfill, because that is when they are *right*.

## What pulling the whole history exposed

Two things only showed up once the mirror stopped being a prefix, both found on a real account
rather than in a test:

- **The account holds unfinished workouts.** 2 of the dev account's 568 have no `end` — sessions
  abandoned at some point in the past. `sql.activeWorkout` selected the newest row with `end IS
  NULL`, so as soon as the backfill brought them down the app restored one as the session in
  progress: an open workout 14,000 hours old. It now requires `synced = 0` as well, which is exactly
  "this device's": the app never posts an unfinished workout (`saveWorkout` runs on finish,
  `syncPendingWorkouts` pushes only `isCompleted && !synced`), so a synced row with no `end` can only
  have come from the server.
- **The two sides were counting different rows**, which is the `synced = 1` note below.

Both were latent before this: `initHistory` would have caused the same thing the moment an abandoned
session landed in the newest twenty. The backfill made them certain instead of unlucky.

## What the summary must not be used for

Two reuses suggest themselves once the counts are on hand. Both are wrong, for one reason: **counts
and heads cannot see an edit or a deletion.**

- **Short-circuiting the launch pulls.** A renamed template or an edited workout leaves both the
  count and the head id identical, so skipping `GET /templates` on a match would pin stale rows in
  place.
- **Skipping rows in the upsync replay** (`docs/2026-09-06.upsync.md`, finding 4). A head only
  proves "nothing here is newer than the server's newest". A row created on this phone while the
  remote leg was closed, on an account that got a newer row from another device meanwhile, sits
  *below* the head — it would be skipped and never backed up. The replay is chatty but correct by
  construction; a `synced` flag is the exact fix, and this is a heuristic.

The backfill is a safe use because its heuristic only decides *whether to do more work*, and doing
too much work is a wasted request rather than a lost row.

## What the mirror can count

`LocalDatabase.mirrorSummary` (`shared/heart_db/lib/src/parts/mirror.dart`) answers in the same
`AccountSummary` shape the server does, over five collections:

| Collection        | Counted as                                                            |
|-------------------|-----------------------------------------------------------------------|
| `customExercises` | `exercises` where `own = 1`                                           |
| `templateFolders` | `template_folders`                                                    |
| `templates`       | with a name — an unnamed draft is a local state the server never sees |
| `workouts`        | `synced = 1` — see below                                              |
| `goals`           | archived included: the account still holds them                       |

The other five the server reports stay out, because absent is honest and zero is not: a zero would
read as "the server has rows I am missing" when it means "this device does not keep that".
`templateShares`, `comments` and `connections` are coach features the app has not shipped;
`workoutImages` are rows no local table mirrors; and `exercisePreferences` is the awkward one — the
server keeps unit, rest timer and chart type in one table while the app spreads the same data over
`exercise_details` and `charts` and holds no preference row ids at all.

The rule for each is *what the server would also count*, because that is the only thing a
comparison against it can mean. `workouts` is `synced = 1` rather than "finished" for a reason found
on device: the account holds abandoned sessions with no `end` — 2 of the dev account's 568 — so
filtering on `end` left the mirror permanently two short of a target it could never reach, and the
backfill re-paged the whole history on every launch. `synced` is also the flag that keeps a workout
in progress on *this* device from inflating the count and hiding a real shortfall of one.

Only `workouts` is compared today. The other four are there because the count is one statement
either way, and because the moment a second collection starts paging this is where its comparison
goes.

## Gaps

- **Counts, not checksums**, and **no child rollups** — the same two limits the server's own doc
  names. Two stores agreeing on count and head can still disagree in the middle, and `workouts`
  counts workout rows rather than their exercises and sets.
- **One backfill, then never again.** A mirror truncated after the mark is written — outside
  `eraseUser`, which clears it — is not noticed. Nothing today does that.
- **No throttle.** 568 workouts is 29 serial requests as fast as the server answers. Fine at
  today's sizes; if histories get much longer this is where a pause between pages goes.
- **`exercisePreferences` cannot be compared from the app side**, so #109's mirror has no
  completeness check of its own.
