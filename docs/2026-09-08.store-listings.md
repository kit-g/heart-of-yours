## Play Console — what it takes

Package `me.heart.android` (dev is `me.heart.android.dev`). Note it does not
match the iOS bundle `me.heart-of.ios`; nothing to fix, but it surprises people
looking for one identifier.

**The listing text was written through the API** on 2026-09-09, with the same
service account CI uses (`github-actions@heart-of-yours`, key at
`secrets/playstore/playstore-sa-key.json` in S3): `edits.insert` →
`edits.listings.update` → `edits.commit`. Graphics go the same way through
`edits.images.upload`.

**`edits.commit` is the permission gate, not `insert`.** With release-only
permissions, `insert`, `listings.update` and `delete` all return 200 and the
commit 403s — so a probe that stops short of committing proves nothing. What
unblocked it was granting **"Edit and delete draft apps"** in Play Console →
Users and permissions. Note the scope of that permission: it covers apps with
no production release. Once Heart is published, editing the live listing is
likely to need **"Manage store presence"** instead, and this will start 403ing
again at the commit.

Everything under *App content* is a console form with no API at all.

### The three that bite

1. **Health apps declaration.** Lists and justifies every Health Connect
   permission one by one, and Google asks for a **video** of the permission
   flow showing each granted permission in use. Reviewed in weeks. This is the
   long pole of the entire Play submission — start it before anything else.
2. **Testing requirement.** A *personal* Play developer account opened after
   Nov 2023 must run a closed test with 12 testers for 14 consecutive days
   before it can apply for production access. An organisation account is
   exempt. If this account is personal, that clock is the release date, and
   nothing else on this page matters until it starts.
3. **Advertising ID.** Firebase Analytics generally merges
   `com.google.android.gms.permission.AD_ID` into the manifest even though the
   app declares no ads, and Play requires the advertising-ID declaration to
   match. It is not in the source manifests; confirm from a *merged* manifest
   after an Android build, then either declare the use or add a
   `tools:node="remove"` for the permission. Guessing either way risks a policy
   rejection.

## Apple privacy labels

**Console only.** There is no App Store Connect API for this: `appDataUsages`,
`appDataUsageCategories` and every publish-state path 404 as non-existent
resources, and none of the 41 relationships on `/v1/apps/{id}` is privacy
related. App Store Connect → App Privacy, in the sidebar under General. It is
app-level rather than per-version and has its own **Publish** button, so it
can sit filled in but unpublished.

Apple offers exactly six purposes — Third-Party Advertising; Developer's
Advertising or Marketing; Analytics; Product Personalization; App
Functionality; Other Purposes. There is no "customer support" purpose; the
bug-report screenshot and text are App Functionality.

Apple's "collect" means *leaves the device*. An account-free install
transmits nothing but diagnostics; the labels must describe the maximum, so
they describe a signed-in user.

**Tracking: none.** No data is used to track, no ad SDK, no third-party
advertising identifier. Answer *No* to the tracking question, and no ATT
prompt is needed.

| Category | Type | Collected | Linked to user | Purpose |
|---|---|---|---|---|
| Health & Fitness | **Fitness** | Yes | Yes | App Functionality |
| Health & Fitness | **Health** | **No** | — | Never leaves the device |
| Contact Info | Email address | Yes | Yes | App Functionality |
| Contact Info | Name | Yes | Yes | App Functionality |
| Identifiers | User ID | Yes | Yes | App Functionality |
| User Content | Photos or Videos (avatar, feedback screenshot) | Yes | Yes | App Functionality |
| User Content | Other User Content (feedback text) | Yes | Yes | App Functionality |
| Usage Data | Product Interaction | Yes | No | Analytics |
| Diagnostics | Crash Data, Performance Data | Yes | No | App Functionality |

Notes for whoever fills the form:

- **Fitness is collected; Health is not.** Workouts sync to the account, so
  they are fitness data that leaves the device. The six metrics read from
  HealthKit do not, and neither does anything derived from them — the guard
  table in `docs/2026-09-05.health-data.md` is the evidence. Do not tick
  *Health* to be safe: an inaccurate label is its own problem, and 5.1.3
  compliance is easier to argue when the label matches the code.
- **Usage Data** is Firebase Analytics, and only the navigator observer —
  screen views, no custom events, no health parameter, ever.
- **Diagnostics** is Sentry: exception type and stack, `tracesSampleRate` 1.0.
  No `setUser` call in `lib/core/env/sentry.dart`, so it is not linked.
- **Photos**: the avatar goes to the account; the in-app feedback screenshot
  goes with the bug report. Health values are redacted out of that capture
  (`RedactedInCapture`), which is worth a sentence in review notes.

## Play Data safety

Same substance, Google's vocabulary. Everything below is **not shared** with
third parties, **encrypted in transit**, and **deletable** — the app deletes
an account from Settings and the server honours it within
`ACCOUNT_DELETION_DEADLINE` (30 days in prod); the deletion URL is
`https://heart-of.me/privacy`.

| Data type | Collected | Optional? | Purpose |
|---|---|---|---|
| Health and fitness → **Fitness info** | Yes | Optional (account only) | App functionality |
| Health and fitness → **Health info** | **No** | — | Device-only |
| Personal info → Email address, Name, User IDs | Yes | Optional (account only) | App functionality, Account management |
| Photos and videos → Photos | Yes | Optional | App functionality, Customer support |
| App activity → App interactions | Yes | No | Analytics |
| App info and performance → Crash logs, Diagnostics | Yes | No | App functionality |

**Health Connect declaration** (App content → Health apps) is a separate
form and the slow one. It must list, and justify one by one, exactly the
permissions in the manifest: the six reads
(`READ_RESTING_HEART_RATE`, `READ_HEART_RATE_VARIABILITY`, `READ_SLEEP`,
`READ_STEPS`, `READ_ACTIVE_CALORIES_BURNED`, `READ_WEIGHT`),
`READ_HEALTH_DATA_HISTORY`, and `WRITE_EXERCISE`. Two things to plan for:

- Google asks for a **video** showing the permission flow and each granted
  permission in use. Budget a recording session; the declaration is reviewed
  in weeks, not days.
- Reading and writing are declared separately, and the answers must match
  `site/privacy.html` word for word in substance.

## Category, age rating, review notes

| | App Store | Play |
|---|---|---|
| Category | Health & Fitness (primary), Sports (secondary) | Health & Fitness |
| Age rating | 4+ | Everyone (IARC) |
| Content | No objectionable content of any kind |

**The Apple questionnaire is answered**, and returns `FOUR_PLUS`. It lives on
the **App Information** page, not the version page, which is why it is easy to
miss; over the API it is
`/v1/appInfos/{id}/ageRatingDeclaration` (the declaration's id is the
appInfo's). Apple's revised questionnaire is in force — `ageAssurance`,
`healthOrWellnessTopics`, `messagingAndChat`, `socialMedia`, `lootBox` and
`ageRatingOverrideV2` are new fields, and `medicalOrTreatmentInformation` is
an enum (`NONE`), not a boolean.

Every content category is `NONE` and every boolean false. The three answers
worth knowing the reasoning for, because the field names are wider than
Apple's definitions:

- **`healthOrWellnessTopics` — no.** Apple defines it as *content that
  provides self-care or lifestyle recommendations*. Heart recommends nothing:
  it records what you did and shows your own readings back. Goals are the
  user's own targets and records are descriptive.
- **`medicalOrTreatmentInformation` — no**, for the same reason. This is the
  field that quietly pushes fitness apps to 12+ when it is ticked out of
  caution.
- **`userGeneratedContent` — no.** Apple means content visible to *other*
  users, and guideline 1.2 requires any app declaring it to ship filtering,
  reporting and blocking. Heart has no feed, no sharing and no comments;
  avatars and feedback screenshots are user-supplied but never published.
  Declaring it invites a reviewer to ask for a report-and-block flow that
  does not exist.

All three flip the day coaching or sharing ships — that is the trigger to
reopen this section.

**App Review notes (Apple)**, worth writing out:

> The app is fully usable without an account — reviewers can log a workout,
> build a template and read every chart straight from a fresh install. A
> demo account is provided for the sync and backup features only.
>
> HealthKit: Heart reads resting heart rate, HRV, sleep, steps, active energy
> and body mass to display them beside the user's training, and writes one
> workout per finished session (start, end, activity type). Health data is
> stored on the device only and is never transmitted — it is excluded from
> the data export, from analytics, and from crash reports.

Sign in with Apple is implemented and offered wherever Google sign-in is, so
guideline 4.8 is satisfied.

## Export compliance

Nothing to answer. `ITSAppUsesNonExemptEncryption` is `<false/>` in
`ios/Runner/Info.plist`, so every build carries the answer and App Store
Connect never shows the prompt — every uploaded build reads back
`usesNonExemptEncryption=False`. If that key is ever removed, the question
returns and blocks each build individually.

**Weights are native to the unit shown.** The app stores kilograms and converts

Goal targets have to be re-entered when the unit system flips, or they show as
converted decimals (`253.5 lbs` from a 115 kg target). Editing the milestone in

deleting and recreating the goal.

Notes for re-running the Android capture: the emulator **needs `-gpu host`**
(software rendering ANRs on the chart-heavy dashboard, and the ANR dialog then
blocks input); the device database is seeded by pulling it with

into `run-as sh -c 'cat > …'` stalls and truncates the file it was writing; and
the Android chrome comes off at **both** ends, `chrome=48` for the status bar
and `chrome_bottom=120` for the tablet taskbar, which the blank-tail trim

--user current --locales <tag>`, which needs no reboot. Text entry for the

by the edge stops reading as a heart and becomes a blob; 1024px will not hold a
14-character logotype *beside* the mark at full contrast without one crowding
the other, which is why the mark is a watermark; and a per-pixel gradient ramp
bands visibly across the mark, so the ground is built at 64×32 and blurred up.
Checked at 384px (the listing size) and against a 16:9 centre crop, since Play
re-crops for other placements.

**Uploaded 2026-09-15.** Apple has 55 framed panels — 11 per locale (8 phone +
3 tablet) across en-US, en-GB, es-ES, fr-FR and ru — every asset `COMPLETE`
with no errors. Play has **70**: the same 8 + 3 per language plus a 3-panel 7"
set in each of the five. `scripts/store_listing.py shots-appstore` /
`shots-play` re-run it, and both replace rather than append.

One deliberate inconsistency: the 10" (iPad) panels show the bench goal at
`50 / 60 kg` and the 7" panels at `50 / 62.5 kg`, because the account's goal
was rewritten between the two shoots. Different form factors on different
store pages; not worth re-shooting the 10" set over.

**Sofia's account was put back on the imperial dataset** once the metric 7"
panels were shot — 92 workouts, goals at 250 lb / 135 lb, verified reading
`214.9 / 250 lbs`, `110 / 135 lbs`, `27795 lbs` and a `137 lbs` body mass. That
is the state Apple review needs: the app takes the unit from the reviewer's
device and only `US`, `LR` and `MM` default to imperial, so pound-native data
is what keeps a US reviewer's numbers round. Every device mirror was wiped
afterwards — the re-import mints new workout ids, so a mirror holding the old
ones would show each session twice.

Two things that cost time and will again:

- **The image types are a closed enum**: `phoneScreenshots`,
  `sevenInchScreenshots`, `tenInchScreenshots`, `tvScreenshots`,
  `wearScreenshots`, `icon`, `featureGraphic`, `tvBanner`. There is no
  `promoGraphic` any more. Read it off the discovery doc rather than guessing.
- **Play's URL segment is `listings`, not `images`.** The resource is called
  `images` in the docs and the client libraries, but the path is
  `/edits/{id}/listings/{language}/{imageType}`. Anything else 404s with an
  HTML error page rather than an API one. The discovery document
  (`/$discovery/rest?version=v3`) is the authority.
- **Apple's display types**: 1320×2868 goes in `APP_IPHONE_67` and 2064×2752 in
  `APP_IPAD_PRO_3GEN_129`; there are no 6.9"/13" enums. Uploading is three steps
  per image — reserve (`POST /v1/appScreenshots`), run the `uploadOperations`
  it returns, then `PATCH` with `uploaded: true` and the MD5. An asset sits at
  `UPLOAD_COMPLETE` for a minute or two before it turns `COMPLETE`; that is
  processing, not failure, but it is worth polling rather than assuming.

A Play `edits.commit` can come back 503 — nothing exists until the commit, so
just run it again.

## Localized copy — written 2026-09-15

Five localizations on both stores: **en-US, en-GB, es-ES, fr-FR, ru** (Play uses
`ru-RU`). The copy is data, in `docs/store-copy/appstore.json` and
`play.json`; `scripts/store_listing.py` pushes it.

```
scripts/store_listing.py read           # what both stores hold now
scripts/store_listing.py push-appstore  # create missing locales, patch all
scripts/store_listing.py push-play      # one edit, every language, commit
```

Edit the JSON, run the push — neither console needs opening, and both pushes
are idempotent. It shells out to `openssl` to sign the JWTs (ES256 for Apple,
RS256 for Play) because this machine has neither `cryptography` nor `PyJWT`,
and it pins the CA bundle to `/etc/ssl/cert.pem` since the python.org build
ships none.

| | Apple | Play |
|---|---|---|
| Resource | `appInfoLocalizations` (name, subtitle, privacy URL) + `appStoreVersionLocalizations` (description, keywords, promo, URLs) | `edits.listings.update` (title, short, full) |
| Written | all five, verified by read-back | all five, committed |

**Creating an `appInfoLocalization` implicitly creates the matching
`appStoreVersionLocalization`.** POSTing the second one then fails 409
`ENTITY_ERROR.ATTRIBUTE.INVALID.DUPLICATE` — the copy goes on with a PATCH.

en-GB is the en-US text unchanged; it exists so the metric screenshots have a
home, since Apple would otherwise fall back to en-US and show pounds in the UK.

Play's full description differs from Apple's in three places, applied per
locale: **Health Connect** rather than Apple Health, **phones and tablets**
rather than iPhone and iPad, and a keyword-bearing opening line, because Play
indexes the full description and Apple does not.

The app name stays **Heart of yours** in every locale, and so does the
subtitle: **`Every beat counts`**. A tagline is part of the mark — nobody ships
"Fais-le" for *Just do it* — so it is not translated, in the stores or in the
app. The app agreed with that only by accident (es and fr were translated, ru
was not); as of 2026-09-15 all five locales are English, and `intl_en.arb`'s
`@motto` description carries the rule so a future translator sees it.

**These translations have not had a native review.** They are marketing copy
written alongside the captions and should go through the same review the app's
strings get before submission. The one thing deliberately *not* translated is
the motto, above.

## Advertising ID

Play asks: *"Your manifest file includes the `com.google.android.gms.permission.AD_ID`
permission… Answer 'yes' or remove this permission."* The honest answer for
Heart is to **remove it**. The app runs no ads, and an advertising ID is a
cross-app tracking identifier inside an app whose own screenshot says *"Your
data. Yours to take or delete."*

It was never declared in `android/app/src/main/AndroidManifest.xml`.
`firebase_analytics` merges it in through play-services-measurement, along with
`ACCESS_ADSERVICES_AD_ID` and `ACCESS_ADSERVICES_ATTRIBUTION`. All three are
now stripped with `tools:node="remove"`, and
`google_analytics_adid_collection_enabled=false` is set on the application —
**both are needed**: the permission is what Play reads, the flag is what the
SDK obeys.

`BIND_GET_INSTALL_REFERRER_SERVICE` is deliberately left. It is install
attribution, not an advertising ID, and it is not what the question asks about.

Verify in the **merged** manifest, never the source one:

    build/app/intermediates/merged_manifest/prodDebug/…/AndroidManifest.xml

**The answer has to match the bundle that is live.** Codes 24 and 28 both carry
the permission, so *No* is only true once a build without it is uploaded — this
landed for **1.8.1**. Answering *No* against an older bundle is a rejection.
